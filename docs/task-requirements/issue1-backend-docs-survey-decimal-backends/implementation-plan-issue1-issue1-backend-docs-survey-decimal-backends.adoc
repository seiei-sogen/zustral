== テストの方針

シームは `run.sh` の外から見える振る舞い、つまり標準出力の結果行と集計行、そして終了状態である。
レポートの主張の正しさは、記録をあらかじめ知っている値と照らすこと（各タスクの「既知の値」）と、一次資料と照らすレビュー（T6）で確かめる。

* 検出できる問題: 記録と食い違う出力の見逃し、未実行を成功に数える誤り、終了状態の誤り、依存の取得失敗の扱いの誤り、clang が扱えない系統の誤った表示、変種だけの記録の扱いの誤り。
* 検出できない問題: プローブが観測すべきことを観測していないこと。これはレポートのレビュー（T6）で補う。

テストのためのスクリプトやフレームワークは足さない。
`run.sh` の照合そのものが、プローブに対する回帰の検査である。
ランナーの分岐は、下の「障害を起こして確かめる手順」で観測する。
どれも作業ツリーを元に戻して終わる。
実装中の成果物は未追跡なので、`git status` だけでは中身の変化が見えない。
手順の前後で `git status --short --untracked-files=all` と `find docs/research/decimal-backend-survey -type f -exec sha256sum {} + | sort` の出力が同じことを確かめる。

== 実装タスク

=== T1: ランナーと `__int128` 系統を端から端まで通す

* Satisfies: REQ-005、REQ-006（不一致の規則）、REQ-008（4変種と2回実行、変種だけの記録）。T2〜T5 の土台。
* Design: 「データの形」「公開インターフェース」「処理の流れと状態」「決定性の演算と入力」
* Depends on: なし
* 対象: `run.sh`、`probes/i128.c`、`expected/i128.txt`
* 変更前後: 前はプローブも再実行手段もない。後は `run.sh` が依存 `gcc` と `clang` を取得し、`i128@{gcc,clang}-{O0,O2}` をビルドして2回ずつ実行し、記録と照合し、集計と終了状態を出す。`--record` が系統の記録と、食い違った変種だけの記録を書き、照合と同じ集計行と終了状態を出す。照合は変種だけの記録があればそれを優先する。1つのプローブで複数の依存を取得できないときは、プローブ表に書いた依存の順で最初に取得できなかったものの理由を出す。
* `i128.c` は、スケール 10^18 の固定小数点で設計文書の演算の組を計算し、`sizeof`、桁の上限、`-fwrapv` での `overflow` と `__builtin_mul_overflow` の検出結果を出す。
* 既知の値: `sizeof=16`、`div_1_3=0.333333333333333333`、`div_2_3=0.666666666666666666`（0への切り捨て）、`add_01_02=0.300000000000000000`、`sum_001_x1000=10.000000000000000000`、`__int128` の最大値 `170141183460469231731687303715884105727`。`overflow`（内部の整数の最大値 ×10）は `-fwrapv` で (2^127−1)×10 mod 2^128 を符号付きに読んだ値、つまり内部の整数 `-10`（`-0.000000000000000010`）になり、`__builtin_mul_overflow` は検出する。`mul_wide` は、35桁の入力をスケール 10^18 の内部の整数へ変換する段階で約38桁を超えるので、`__builtin_mul_overflow` が検出する。プローブは値を出さず `mul_wide=overflow_detected` を出す。
* テスト: 記録がない状態で4行の `不一致` を確かめる。既知の値と照らしてから `--record` を実行し、4行の `一致` を確かめる。続けて「改ざん」「変種の記録」「変種の食い違いの記録」「繰り返しの食い違い」を実行する。
* Done when:
** 「記録と食い違う出力は失敗として見える」を「改ざん」で確認できる。
** 「結果が一致しない組み合わせは隠さず示される」の表示側を、「改ざん」の変種 id 付きの差分と、「変種の食い違いの記録」の `一致*` の表示で確認できる。
** 作業ツリーを戻した後の `run.sh` が `一致 4 / 不一致 0 / 未実行 0` で終了状態 0 になる。これは4変種がそれぞれ2回とも同じ記録に一致したことを示す（REQ-008 の最適化レベル間、gcc と clang の間、繰り返し）。
** 「繰り返しの食い違い」で、1回目と2回目の食い違いが不一致として表示される（REQ-008 の繰り返し）。

=== T2: GCC `_Decimal128` 系統と clang の未実行

* Satisfies: REQ-001（GCC 分）、REQ-002、REQ-008
* Design: 依存表の `clang-dfp`、「決定性の演算と入力」
* Depends on: T1
* 対象: `probes/d128.c`、`expected/d128.txt`、`run.sh` の依存 `clang-dfp`
* 変更前後: 前は d128 の行がない。後は `d128@gcc-*` が一致し、`d128@clang-*` が依存 `clang-dfp` で未実行になる。
* `d128.c` は `float.h` の `DEC128_MANT_DIG`、`DEC128_MIN_EXP`、`DEC128_MAX_EXP` と、演算の組の結果を出す。
libdfp なしの GCC には丸めモードを切り替える API と quantize の関数がないと見込んでおり、`d128.c` は `quantize_1005_<mode>` を出さない。この見込みは T2 で gcc 16.2.0 のヘッダと libgcc の公開シンボルを見て確かめ、レポートでは丸めモードの扱いを一次資料で示す。見込みに反して API が見つかれば、`d128.c` もその API で切り替えられるモードごとに `quantize_1005_<mode>` を出す。
glibc の `printf` には `_Decimal128` の書式がないので、プローブが BID の16バイトを符号、指数、係数に分けて `<符号><係数>E<指数>` の形で出す。無限大と NaN は BID の組み合わせビットで見分けて `inf` と `nan` と出す。
* 既知の値: IEEE 754-2008 の decimal128 の定義から、精度 p=34 と emax=6144。C の `float.h` は指数を emax+1 で定義するので、`DEC128_MANT_DIG=34`、`DEC128_MAX_EXP=6145`、`DEC128_MIN_EXP=-6142`。出力の形で書くと、`div_1_3=+3333333333333333333333333333333333E-34`（3が34個）、`div_2_3=+6666666666666666666666666666666667E-34`（6が33個と7）、`add_01_02=+3E-1`、`sum_001_x1000=+1000E-2`。`mul_wide` は、35桁の入力が読み込みで34桁に丸められ（最後の5は丁度半分で、偶数の4に丸まる）、`mul_wide=+1234567890123456789012345678901234E+2`。`overflow=+inf`。
* テスト: 既知の値と照らしてから `--record` を実行し、`d128@gcc-O0` と `d128@gcc-O2` の一致と、`d128@clang-*` の未実行を確かめる。
* Done when: 「clang でコンパイルできない系統は clang 比較を未実行と示す」を、`未実行  d128@clang-O0: clang-dfp: error: GNU decimal type extension not supported` の形の2行で確認でき、集計の一致にそれらが数えられていない。

=== T3: mpdecimal 系統

* Satisfies: REQ-001、REQ-002（確保と解放を含む）、REQ-008
* Design: 依存表の `mpdecimal`、「観点ごとにプローブが出すもの」
* Depends on: T1
* 対象: `probes/mpd.c`、`expected/mpd.txt`
* 変更前後: 前は mpd の行がない。後は `mpd@{gcc,clang}-{O0,O2}` の4行が一致する。
* `mpd.c` は `MPD_MAX_PREC`、`MPD_MAX_EMAX`、`MPD_MIN_EMIN`、丸めモードの一覧、`mpd_ieee_context(&ctx, MPD_DECIMAL128)` での演算の組、`overflow` の結果と状態フラグを出す。`mpd_mallocfunc` などを数える関数に差し替え、値の生成と演算ごとの確保回数を出す。
* 既知の値: 演算の組は T2 と同じ値（decimal128 と同じ精度34桁。出力の形は mpdecimal の `mpd_to_sci` に従う）で、`overflow` は無限大と `MPD_Overflow` のフラグ。確保回数は、mpdecimal の公式ドキュメントの記憶管理の節と `mpd_qnew` の説明から決まる値と照らす。ドキュメントから回数が決まらなければ、記録の値は観測値として扱い、レポートでは「値の生成にヒープ確保が要る（1回以上）」の主張だけに使う。`MPD_MAX_PREC` などは、プローブが読むヘッダではなく mpdecimal の公式ドキュメント（libmpdec の Context の節）に書かれた 64ビット環境の値と照らす。`quantize_1005_<mode>` は丸めの定義から、`MPD_ROUND_UP`、`CEILING`、`HALF_UP`、`05UP` で 1.01、`DOWN`、`FLOOR`、`HALF_DOWN`、`HALF_EVEN`、`TRUNC` で 1.00（`05UP` は0方向に丸めた最後の桁が0なので0から遠い側へ丸める）。
* テスト: 既知の値と照らしてから `--record` を実行し、4変種の一致を確かめる。
* Done when: `run.sh` が `mpd@{gcc,clang}-{O0,O2}` の4行を `一致` で出す。

=== T4: Intel DFP と libdfp の系統

* Satisfies: REQ-001（libdfp と Intel DFP の区別）、REQ-002、REQ-006（未実行の規則）、REQ-008
* Design: 依存表の `libdfp` と `intel-dfp`、プローブ表の libdfp のビルド条件
* Depends on: T1、T2（`clang-dfp`）
* 対象: `probes/intel.c`、`probes/libdfp.c`、`expected/intel.txt`、`expected/libdfp.txt`、`run.sh` の依存2つ
* 変更前後: 前は intel と libdfp の行がない。後は `intel@*` の4行と `libdfp@gcc-*` の2行が一致し、`libdfp@clang-*` の2行が未実行になる。
* libdfp の tarball の sha256 をここで計算し、`run.sh` に固定する。
* `intel.c` は5つの丸めモード（`BID_ROUNDING_TO_NEAREST` など）での `quantize_1005_<mode>` と、演算の組、`overflow` のフラグを出す。
* `libdfp.c` は `strtod128` と `strfromd128` で入出力する（どちらも実験3で動いた）。丸めモードは `fe_dec_setround` で切り替えて `quantize_1005_<mode>` を出す。`fe_dec_setround` は実験で使っておらず未確認である。リンクできなければ、丸めモードの一覧はヘッダの引用で示し、プローブは既定のモードの結果だけを出す。
* 既知の値: 演算の組は T2 と同じ値で、`overflow` は無限大とオーバーフローのフラグ。`quantize_1005_<mode>` は IEEE 754-2008 の丸めの定義から、最近接偶数で 1.00、最近接の0から遠い側で 1.01、正の無限大方向で 1.01、負の無限大方向と0方向で 1.00。
* テスト: 既知の値と照らしてから `--record` を実行する。gcc の変種と `intel@clang-*` の一致、`libdfp@clang-*` の未実行を確かめる。続けて「curl 遮断」を実行する。
* Done when:
** 「依存を取得できないプローブは未実行として表示される」を「curl 遮断」で確認できる。未実行の行に理由があり、集計の一致にそれらが数えられず、ほかが一致すれば終了状態が 0 である。
** 「clang でコンパイルできない系統は clang 比較を未実行と示す」を、`libdfp@clang-O0` と `libdfp@clang-O2` の未実行の行でも確認できる。

=== T5: Zustral FFI プローブ

* Satisfies: REQ-007
* Design: 「Zustral FFI プローブ」「手間の上限（REQ-007）」
* Depends on: T1、T2（既知の値）、T3（`mpdecimal`）
* 対象: `probes/ffi/Probe.aum`、`probes/ffi/shim.c`、`probes/ffi/UnitReturn.aum`、`expected/ffi.txt`、`expected/ffi-unit-return.txt`、`run.sh` の依存 `zustral`
* 変更前後: 前は ffi の行がない。後は `ffi` と `ffi-unit-return` が一致し、`ffi` は一致したときも実際の出力を結果行の下に表示する。
* `Probe.aum` は、`mpd_qnew` を直接 `Address[Nat8]` で受け、`void` を返す mpdecimal の関数と、16バイトの領域越しの `_Decimal128` と `__int128` の演算を、シム経由で呼ぶ。ポインタの値は出力しない。出すキーは `mpd_qnew_direct`（直接束縛した `mpd_qnew` が NULL でなかったかを `ok` か `null` で出す）、`mpd_add_01_02`、`d128_add_01_02`、`i128_add_01_02` の4つで、値の形は各系統のプローブと同じにする。
* `UnitReturn.aum` は、`void` の C 関数を戻り値 `Unit` で束縛して呼ぶ。コンパイラの出力と `exit=` 行がそのまま記録になる。
* 既知の値: `ffi` の演算結果は T1〜T3 と同じ値。`ffi-unit-return` は `lib/CodeGen.ml:587-591`（戻り値の型の変換）と `lib/CodeGen.ml:556-557`（`Unit` を拒む分岐）から、`Not allowed` を含むエラーと 0 でない終了状態。

== 判断から学べること

計画で増えた判断だけを置く。要件側の学びは要件定義書を参照する。

. ランナーの分岐は、テスト用のフレームワークを足さずに、実際の失敗条件を外から起こして確かめる。
** 兆候: 検査対象が「外部の取得に失敗したとき」「記録と食い違ったとき」のような環境由来の分岐で、関数単位に切り出すとモックが要る。
** 使える条件: 失敗条件を環境変数やファイルの書き換えで安全に起こせ、元に戻せるとき。
** 使わないほうがよい条件: 失敗を起こすのに破壊的な操作や外部サービスの状態変更が要るとき。
** 関連: 「テストの方針」の表、設計文書の「要件との対応」。
** 検索語: fault injection、black-box testing of shell scripts。
. 出力を記録して照合する検査では、記録を作る前に、知っている値と手で照らす。
** 兆候: `--record` のように、今の出力をそのまま正本にする仕組みがある。
** 使える条件: 仕様や算術から独立に決まる値が少なくとも一部にあるとき。
** 使わないほうがよい条件: 出力が環境の観測そのもので、独立に決まる値がないとき（コンパイラのエラー文など）。その場合は出典と照らす。
** 関連: 「テストの方針」の既知の値、tdd-matt-p の同語反復のアンチパターン。
** 検索語: golden file testing、snapshot testing pitfalls、test oracle。
. nix の依存がキャッシュ済みなら、クライアント側の `https_proxy` で curl の取得だけを止められる。
** 兆候: nix の依存と curl の依存が混在し、片方だけを取得失敗にしたい。
** 使える条件: 固定した nixpkgs の flake 入力とストアのパスが取得済みのとき。
** 使わないほうがよい条件: 初回の実行。flake の入力はクライアントが取得するので、nix の依存も止まる。
** 関連: 「テストの方針」の「curl 遮断」。この仮説は T4 で確かめる。
** 検索語: nix-daemon proxy environment、impure env vars。
