2. 背景と目的

Zustral（Austral のフォーク）に10進数（Decimal）を持ち込む言語仕様を固める途中にある。 Decimal が乗れる実行時表現の候補が、実際のところ何がどう違うのかが分かっていない。 この違いが、下流のチケットの判断を縛る。

  • 0004「スケールは型に入るか、値に入るか」（0001 と 0003 にブロックされる）

  • 0005「Decimal は線形リソースか、値型か」（0001 にブロックされる）

  • 0008「桁あふれを例外なしでどう扱うか」（0004 と 0005 の後に続く）

チケット番号 000N は issue #N に対応する。

目的

0004・0005・0008 を詰める人が、3系統の候補の違いを、このマシンで再実行できる証拠か一次資料に裏付けられた事実として読めるようになること。

利用者は2種類いる。

レポートの読者

下流チケットで壁打ちする人。事実と根拠を読み、選定の材料にする。

プローブの再実行者

レポートの主張を疑う人。1つのコマンドでプローブを再実行し、出力とレポートを照らし合わせる。

3. 対象範囲と対象外

3.1. 対象

3系統（issue が「最低でも」と挙げたもの）:

  • mpdecimal（Python の decimal が使っている任意精度10進ライブラリ）

  • IEEE 754-2008 decimal128（GCC の _Decimal128 / libdfp / Intel DFP ライブラリ）

  • 自前の固定小数点（__int128 にスケールを添える）

5観点（issue の「知りたいこと」）:

  1. 確保と解放のモデル

  2. 精度と桁数の上限、丸めモードの品揃え

  3. C ABI からの呼び出しやすさ

  4. 依存とライセンス、ビルドの重さ、プラットフォーム移植性

  5. 演算結果の決定性

成果物:

  • 調査レポート（日本語の文書）

  • レポートの事実を裏付けるプローブと、それを1コマンドで再実行する手段

  • issue #1 の解消と、地図 issue #9 への記録

3.2. 対象外

  • バックエンドの選定そのもの。0004・0005・0008 の仕事である。

  • コンパイラ（lib/）と stdlib（standard/）への decimal 実装。

  • issue #2〜#8 の編集。

  • リポジトリ内の docs/wayfinder/ の変更。トラッカーは GitHub Issues に移っており、docs/wayfinder/ の扱いは別の PR が受け持つ。

4. 要件

レポートの置き場所、プローブの言語とファイル構成、記録した出力の置き場所、決定性を確かめる演算と入力の選び方、Zustral の FFI プローブの組み立て方は設計で決める。 既定の置き場所の候補は docs/research/decimal-backend-survey/ である。

4.1. 内容の網羅

REQ-001

レポートは、3系統それぞれについて、5観点すべての事実を示さなければならない。 decimal128 系統では、各主張が GCC の _Decimal128、libdfp、Intel DFP のどれについてのものかを区別しなければならない。

REQ-002

レポートは、観点ごとに少なくとも次を示さなければならない。

  • 確保と解放: 1つの値を作るのにヒープ確保が要るか。値のサイズが固定か。使い終わった値に明示的な解放が要るか。

  • 精度と丸め: 有効桁数と、指数またはスケールの範囲。提供される丸めモードの一覧。結果が上限を超えたときに何が起きるか。

  • C ABI: 下記 REQ-007 の内容。

  • 依存とライセンスとビルドと移植性: 依存するライブラリ、ライセンス名、このマシンでの入手手段とビルドの重さ（パッケージで入るか、ソースからのビルドが要るか）、公式に支えるプラットフォーム。

  • 決定性: 下記 REQ-008 の内容。

4.2. 根拠の付け方

REQ-003

レポートは、事実を述べる文ごとに、次の少なくとも一方を根拠として示さなければならない。 (a) このマシンで再実行できるプローブの出力。 (b) 一次資料（公式ドキュメント、ソースコード、仕様、ライセンスファイル）の URL と版。

REQ-004

If 主張がこのマシンで観測できない（他プラットフォームでの挙動など）なら、then レポートはその主張に「出典のみ・未実測」と明記しなければならない。 根拠を示せない内容は事実として書かず、未確認事項として分けなければならない。

@REQ-003
Scenario: このマシンで観測できる主張はプローブ出力を根拠に持つ
  Given レポートに「nixpkgs（rev 674a2028）の gcc 16.2.0 の _Decimal128 は有効桁数34桁」という主張がある
  When 読者がその主張の根拠を見る
  Then 根拠として、その値を出力するプローブとその出力が示されている

@REQ-004
Scenario: このマシンで観測できない主張は出典のみと明記される
  Given このマシンは x86_64 であり、レポートに AArch64 での _Decimal128 の挙動についての主張がある
  When 読者がその主張を見る
  Then その主張には「出典のみ・未実測」の表記と一次資料の URL と版が付いている

4.3. プローブの再実行

REQ-005

プローブは、再実行者が1つのコマンドで全部を再実行できなければならない。 レポートは、そのコマンドと、再実行に必要な前提（nix、C コンパイラなど）を示さなければならない。 プローブ出力を根拠にする主張は、どのプローブの出力に基づくかを特定できなければならない。

REQ-006

When 再実行したプローブの出力が、記録した出力と一致しないとき、再実行コマンドは一致しなかったプローブを表示し、失敗の終了状態で終わらなければならない。 If プローブの依存（ライブラリやコンパイラ）をこのマシンで取得できないなら、then 再実行コマンドはそのプローブを未実行として理由とともに表示し、成功の件数に含めてはならない。 未実行だけでは失敗の終了状態にしない。取得できない依存が恒常的にあっても、記録との食い違いを終了状態で検出できるようにするためである。 レポートは、未実行になったプローブに依存する主張を「出典のみ・未実測」として扱わなければならない。

@REQ-006
Scenario: 記録と食い違う出力は失敗として見える
  Given あるプローブの出力が、記録した出力と異なる
  When 再実行者が再実行コマンドを実行する
  Then 一致しなかったプローブの名前が表示される
  And コマンドは失敗の終了状態で終わる

@REQ-006
Scenario: 依存を取得できないプローブは未実行として表示される
  Given あるプローブが依存するライブラリを、このマシンで取得できない
  When 再実行者が再実行コマンドを実行する
  Then そのプローブは未実行として、取得できなかった理由とともに表示される
  And そのプローブは成功の件数に含まれない
  And ほかのプローブがすべて記録と一致すれば、コマンドは成功の終了状態で終わる

4.4. C ABI と Zustral からの呼び出し

REQ-007

レポートは、各系統の10進値を Zustral の Foreign_Import で扱えるかを示さなければならない。 示す内容は、値のまま渡せるか、ポインタ越しなら渡せるか、C の薄い包み（シム）が要るか、である。 Zustral 側の制約（FFI が受け付ける型）は、コンパイラのソースを根拠に示さなければならない。

Where Zustral コンパイラをこのマシンでビルドできる場合、レポートは、各系統を Foreign_Import で呼ぶ Zustral プログラムを実行した結果を根拠にしなければならない。 If コンパイラのビルドが失敗する、または設計で決めた手間の上限を超えるなら、then レポートはその理由を記録し、C だけのプローブとコンパイラのソースの引用を根拠にしなければならない。

@REQ-007
Scenario: コンパイラをビルドできれば Zustral プログラムで確かめる
  Given Zustral コンパイラをこのマシンでビルドできる
  When 再実行者が再実行コマンドを実行する
  Then 各系統を Foreign_Import で呼ぶ Zustral プログラムの出力が表示される

@REQ-007
Scenario: コンパイラをビルドできなければ理由を残して C だけで確かめる
  Given Zustral コンパイラのビルドがこのマシンで現実的でない
  When 読者がレポートの C ABI の節を読む
  Then ビルドできなかった理由が書かれている
  And 根拠は C だけのプローブとコンパイラのソースの引用である

4.5. 決定性

REQ-008

レポートは、各系統について同じ入力の演算結果が、このマシンで次のあいだで一致するかを示さなければならない。

  • 少なくとも2つの最適化レベル

  • gcc と clang。clang を取得でき、その系統をコンパイルできる場合に限る

  • 同じ実行を繰り返したとき

If ある組み合わせで結果が一致しないなら、then レポートはその組み合わせと各出力をそのまま示さなければならない。 プラットフォームをまたいだ一致は、出典がある場合だけ「出典のみ・未実測」として示し、実測したと書いてはならない。

@REQ-008
Scenario: 結果が一致しない組み合わせは隠さず示される
  Given ある系統の同じ入力の演算が、最適化レベルによって異なる結果を出す
  When 読者がレポートの決定性の節を読む
  Then 異なる結果を出した最適化レベルと、それぞれの出力が示されている

@REQ-008
Scenario: clang でコンパイルできない系統は clang 比較を未実行と示す
  Given ある系統のプローブを、このマシンで取得した clang ではコンパイルできない
  When 再実行者が再実行コマンドを実行する
  Then その系統の clang 比較は未実行として理由とともに表示される

6. 前提と制約

判断に効いた事実だけを置く。ほかの調査結果は事前調査レポートを参照する。

  • Zustral の FFI は128ビット整数を持たない。整数の幅は 8/16/32/64/ByteSize/Index だけである（lib/Type.ml:22-29）。

  • Zustral の FFI はレコードの値渡し、Unit の戻り値、参照を受け付けない（lib/CodeGen.ml:554-591）。

  • コンパイラの CLI には、追加の C ファイルやリンクするライブラリを渡すフラグがない。外部ライブラリとのリンクは --target-type=c の出力を自分で C コンパイラに渡す（lib/CliParser.ml:55、lib/Util.ml:202-203）。

  • Foreign_Import の既存例が examples/ffi/FFI.aum:1-14 にある。

  • このマシンの gcc 13.3.0 は DECIMAL_BID_FORMAT=1、DEC128_MANT_DIG=34、SIZEOF_INT128=16 を定義する（echo | gcc -dM -E - の出力）。

  • clang は PATH にない。nixpkgs（rev 674a2028661e）から clang 21.1.8 を取れる。

  • nixpkgs には mpdecimal 4.0.1（BSD-2-Clause）がある。libdfp、Intel DFP、decNumber の名前のパッケージは見つからなかった。

  • wayfinder のトラッカーは GitHub Issues である。地図 issue #9 の「トラッカーの約束（GitHub Issues）」では、確保は issue へのアサインで行い、解消は解消コメントの投稿、issue のクローズ、地図の「ここまでの決定」への1行で行う。issue #1 は seiei-sogen にアサイン済みで、確保は済んでいる。

7. 正常系、境界条件、失敗時の結果

正常系

再実行コマンドが全プローブを実行し、出力がレポートの記録と一致して、成功の終了状態で終わる。

境界条件

依存を取得できないプローブ（REQ-006）、clang でコンパイルできない系統（REQ-008）、コンパイラをビルドできない場合（REQ-007）。どれも未実行や理由として見え、成功に数えない。

失敗時の結果

出力が記録と食い違えば、再実行コマンドがそのプローブを名指しして失敗する（REQ-006）。

9. データ移行、互換性、セキュリティ、運用への影響

  • データ移行と互換性: なし。コンパイラと stdlib を変えない。

  • セキュリティ: プローブは外部入力を受け取らない。nix で取得するパッケージは nixpkgs の rev 674a2028661e550a97400c1cc992b9cca9a668a1 に固定し、再実行で版が変わらないようにする。版はレポートに記録する（REQ-003 の「版」）。

  • 運用: issue #1 は REQ-010 の解消でクローズする。PR 本文の Closes #1 は、マージ時に #1 が開いていた場合の閉じ忘れを防ぐ。

10. 未確定事項

どれも、結果ごとの扱いを REQ-006・REQ-007・REQ-008 が決めているため、このまま設計と実装に進める。

  1. Zustral コンパイラが、このマシンの nix dev shell で現実的な時間にビルドできるか。確認方法: flake.nix の dev shell で make を実行する。結果は REQ-007 の分岐を決める。

  2. mpdecimal のヘッダと、Zustral が生成する au_* 型の extern 宣言を同じ翻訳単位に置いたときに型が衝突するか。確認方法: 小さな Zustral プログラムを --target-type=c で出し、mpdecimal とリンクする。結果は FFI プローブの組み立て方を決める。

  3. libdfp と Intel DFP を、このマシンでソースからビルドできるか。確認方法: 各プロジェクトの公式リポジトリのビルド手順を試す。できなければその主張は出典のみになる。

  4. nixpkgs の clang 21.1.8 が、このマシンで _Decimal128 をコンパイルできるか。確認方法: nix shell nixpkgs#clang で小さなプログラムをコンパイルする。できなければ REQ-008 の clang 比較は未実行になる。

11. 安全面でgrillingで対象外としたこと

論点 区分 見送った理由 後から足す条件

演算速度の計測

対象外

issue の5観点に実行速度は含まれない。数値を出すとベンチマークの条件管理が要り、事実の調査から外れる。

0005 などの壁打ちで、速度が選定を分ける論点になったとき。

他プラットフォーム（AArch64、macOS、Windows）での実測

対象外

このマシンで観測できない。出典のみとして扱えば下流の判断材料は欠けない。

別のマシンや CI で同じプローブを走らせられるようになったとき。

プローブを test-programs/ や CI に組み込むこと

12. 判断から学べること

実装前の判断として記す。効果は実証していない。

  1. 調査と選定を分けたチケットでは、調査レポートに推奨を書かない。

    • 兆候: research チケットの後ろに、それにブロックされる grilling チケットが並んでいる。

    • 使える条件: 下流に選定を担う場が別にあるとき。

    • 使わないほうがよい条件: 調査と決定が同じ人・同じ場で完結し、推奨がないと次に進めないとき。

    • 関連: REQ-009、採用した意思決定の表。

    • 検索語: wayfinder research ticket、separation of fact-finding and decision。

  2. 観測できる主張と出典だけの主張を、文の単位で分ける。

    • 兆候: 「プラットフォームをまたいで同じ答えになるか」のように、手元で確かめられない性質を問われている。

    • 使える条件: 読者が主張を再実行で確かめる手段を持つとき。

    • 使わないほうがよい条件: すべての主張が出典に基づく文献調査で、再実行する対象がないとき。

    • 関連: REQ-003、REQ-004、REQ-006。

    • 検索語: reproducible research、evidence labeling。

  3. C ライブラリの呼びやすさは、ライブラリ側より先に言語の FFI の型対応表で決まることがある。

    • 兆候: 比べたい値型が128ビットや構造体の値で、言語の FFI がその幅や値渡しを持たない。

    • 使える条件: C バックエンドや FFI を持つ言語から C ライブラリを評価するとき。

    • 使わないほうがよい条件: 言語の FFI が対象の型を直接表せるとき。

    • 関連: REQ-007、lib/CodeGen.ml:554-591、lib/Type.ml:22-29。

    • 検索語: FFI type mapping、C ABI 128-bit by value、shim function。
