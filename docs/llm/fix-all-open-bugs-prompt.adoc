= 開いている不具合を全部直すための作業指示

コーディングエージェントに渡す作業指示である。1 回のセッションでは終わらない。
セッションを何度も立て、どのセッションも、この文書のとおりに続きから進める。

== 使い方

セッションの最初に、次の 1 行を渡す。

[source]
----
/poteto-mode docs/llm/fix-all-open-bugs-prompt.adoc を読んで、そのとおりに進める。
----

進み具合は、この文書ではなく、`docs/plan.md` の台帳（下の「台帳」）に書く。
方針を変えたときだけ、この文書の「決めた方針」を書き換える。

返答は日本語にする。主張ごとに「実測」「推論」を付ける。

== 台帳

最初のセッションで作る。後のセッションは、続きから始める。

`docs/plan.md` の C9 の表を、不具合 1 件が 1 行になるように書き直す。まとめ issue は、項目ごとに
行を分ける（`#163 の 4` のように書く）。9 節の C の項目と 8 節の L の項目が持つ issue も、行にする。
各行に、次の状態のどれかを書く。

* **未。** 今のコンパイラで再現した。まだ直していない。
* **済み。** 直した。コミットを書く。
* **再現せず。** 今のコンパイラでは起きない。どのコミットで直ったかが分かれば書く。
* **重複。** 別の行と同じ根である。その行を書く。
* **決定待ち。** 下の「決めた方針」にない決定が要る。

台帳を作るために、全部の項目の再現を、今のコンパイラで動かす。項目が多いので、読むだけの
エージェントに分けて頼んでよい。ファイルを変えさせず、再現のプログラムと出力を返させる。
返ってきた結果は、怪しいものを自分で動かし直す。

== 決めた方針

だれが決めたかを、項目ごとに書く。「前のセッションの推奨」は、利用者がまだ確かめていない。
推奨のまま進めてよいが、issue に書くときは、推奨のまま進めたと書く。

* **名前（#163 の 1 と 2、#138、#28、#86、#51）。** 利用者が決めた。1 つの名前は、1 つのものしか
指さない。
** 変数（引数、`let`、`var`、分解の束縛、`case` の束縛、`borrow` の名前、`for` の変数）は、
取り込んだ名前と同じ名前を持てない。自動で取り込まれる `Austral.Pervasive` の名前も、
明示した `import` の名前も、別名も含む。今は、モジュールの宣言と同じ名前だけをエラーにしている
（`TypingPass.check_var_doesnt_collide_with_decl`）。
** モジュールの宣言と取り込んだ名前の衝突、union の case どうしと case とレコードの衝突、
組み込みの型と同じ名前の型の宣言を、宣言の位置でエラーにする（`docs/plan.md` の C4）。
** 既存のプログラムで、この規則に当たる名前は、変える。何本が当たったかを数える。
** これが入ると、`ReturnCheck` が有効範囲の変数を集める仕組み（#157 の 1 の修正）は要らなく
なるはずである（推論）。確かめてから、消す。
** 算術の演算子は、メソッドを名前で探さず、`Austral.Pervasive` のメソッドを直接呼ぶ（#138）。
* **型引数（#156、#158 の 3 と 4、#142 の 2 と 4、#128 の 004、007、012）。** 利用者が決めた。
呼ばれる側の型引数を付け替える形で直す。#151 の箇所ごとの修正を、1 か所の規則にまとめる。
* **評価順（#53）。** 計画の推奨（C2）。左から右にする。
* **`printSpan`（#60）。** 計画の推奨（C7）。`Printable` から外す。
* **符号と単項のマイナス（#26、#162、#48、#47）。** 前のセッションの推奨。`docs/plan.md` の
L1 から L3 に従う。単項の `-` を、引き算とは別の節として型検査まで運ぶ。符号は、リテラルの
一部として読まない（`a -1` は引き算である）。細かい所は、試作で決めて、issue に書く。
* **メソッド自身の型引数（#157 の 2、#144 の 7）。** 前のセッションの推奨。メソッド自身の型引数は、
領域だけにする。領域でない型引数は、宣言の位置でエラーにする。
* **`!ref := e`（#34）。** 前のセッションの推奨。構文解析を広げて、受け付ける。`docs/paths.md` を
仕様とする。
* **定数の書き込みの借用（#144 の 6）。** 前のセッションの推奨。エラーにする。
* **`Type` の宇宙で型引数のない型（#144 の 5）。** 前のセッションの推奨。宣言の位置でエラーにする。
* **`error.html` と一時ファイル（#33）。** 前のセッションの推奨。`error.html` は、既定では書かない。
オプションで出力先を指定したときだけ書く。一時ファイルは、C のコンパイルが終わったら消す。
期待値が大量に変わるので、最後の波で、これだけのコミットにする。

ここにない決定が要るときは、実行して決着するものは試作で決め、issue に書く。好みや方針の判断は、
その行を「決定待ち」にして、次へ進む。止まらない。最後の報告に、推奨を付けて並べる。

== 1 件ごとの進め方

. 今のコンパイラで、再現プログラムを動かし、再現する。
. 失敗するテストを `test-programs/suites/`（コマンドラインは `test-programs/cli/`）に足し、
先にコミットする。直す前のコンパイラで失敗することを、実行して見る。
* エラーを期待するテストは、`austral-stderr.txt` がないと「通ることを期待する」テストに
なる。中身を `{}` にして置き、直したコンパイラで `runner.py <スイート> <テスト> --replace-stderr`
を使って期待値を取り、目で確かめる。
* テストの番号は、同じスイートの最後の番号の次にする。数ではなく、名前を見て決める。
* 修正の範囲を確かめる「通ることを期待する」テストも足す（近い形の正しいプログラム）。
* 今の振る舞いを「おかしい」と書いて固定しているテスト（#144、#124、#142）は、期待値を書き直す。
. 根本の原因で直す。同じ欠陥を持つ箇所を、ほかにも探す。
. 等価性の検査を、直前のコミットとの比較で行う（テストをコミットした後に
`tools/refactoring/check.sh HEAD --quick`）。違うと出るのは、直した不具合を固定していたテストと、
新しいテストだけのはずである。
* `check.sh` は、違うプログラムを最初の 60 行しか出さない。`tools/refactoring/equivalence.py` の
`snapshot` と `compare` を直接使い、`DIFFERS` の行を全部見る。
* 違いが出たテストは、コミットメッセージに並べる。
. `tools/refactoring/coverage.sh --unexecuted --check` を走らせる。
`expected/unexecuted-lines.tsv` は空のまま保つ。エラーの文面を足したら
`coverage.sh --messages` も走らせる。
. 記録を取り直す（`measure.sh --record`、`unused-exports.sh --record`、
`unpinned-messages.py --record`）。
. 台帳の行を「済み」にし、`docs/check-plan.py` の `FIXED` に番号を足す（閉じる issue だけ）。
振る舞いの規則が変わったら、`docs/walkthrough.md` を直す。
. issue に、原因、直し方、テスト、コミットを書く。1 つの不具合だけの issue は閉じる。
コミットに `Fixes #n` を入れる。まとめ issue は、直したものだけをコメントに書き、本文の該当する
項に直したことを書き足す。全部の項が済みか、再現せずか、別の issue へ移ったら、閉じる。

== 波ごとにすること

* 作業の始めのコミットとの比較（`git tag -f refactoring-base <そのセッションの始めのコミット>` の後、
`tools/refactoring/check.sh refactoring-base`）。違いは、その波までに足したテストと、期待値を
書き直したテストだけのはずである。本数を数え、説明の付かない違いがないことを見る。
* `coverage.sh --record`。
* `docs/check-plan.py` に、開いている issue の番号を渡して走らせる。2026-11-16 の時点で、指摘は
16 件（閉じた issue を計画が引用しているもの）である。増えないことを見る。この 16 件も、
道具の波で直す。
* レビュー（下）。
* `docs/plan.md` の冒頭の「状態」に、どの波まで終わったかと、作業ブランチの名前を書く。
* push する。

== レビュー

* 波が終わるごとに、独立したエージェントにレビューをかける。修正 1 つにつき 1 人。並べて走らせる。
1 件につき最大 3 回まで。2 回目は、1 回目の指摘でコンパイラのコードを変えたときだけかける。
* レビュー役には、結論ではなく、差分と目的を渡す。次を頼む。
** 直し残した穴を、実際にプログラムを書いてコンパイルして探す。
** 修正の前は通っていた正しいプログラムを、新しく拒んでいないかを探す。
** 修正の前と後のコンパイラの実行ファイルを渡し、前後を比べてもらう。
1 件を直すたびに、コンパイラを別の名前で写しておく。
* レビューの指摘は、直す前に自分で再現する。
* 波の最後に `/code-review high --fix` をかける。作業ツリーに残った修正は、
前後で再現を動かし、等価性の検査を回してからコミットする。

== 守ること

* プルリクエストを作ることと、master へ直接 push することは、利用者が頼むまでしない。
* 修正の途中で、台帳にない不具合を見つけたら、issue にし、台帳に行を足す。同じ波に入るものは、
その波で直す。入らないものは、後の波に回す。issue を作る前に、同じものがないかを探す。
前のセッションは、#26 を見落として #162 を作った。
* 前は通っていた正しいプログラムを、修正が通さなくするときは、方針に書いてあるものだけにする。
書いていないものは、直すか、「決定待ち」にする。黙って通さなくしない。
前のセッションでは、#25 の修正が、型変数の型の値への単項のマイナス（`-x`）を通さなくした。
レビューが見つけるまで、気づかなかった。
* コミットメッセージに書く数（レビューの回数、違いの本数）は、実行して見た数にする。
コミットのハッシュを書き換えたら（`--amend`）、メッセージの中で引用したハッシュを確かめ直す。
* コンパイラは、失敗するとカレントディレクトリに `error.html` を書く。テストの実行は
`FAILURES.txt` を書く。コミットに入れない。
* 直す前のコンパイラで `runner.py` を走らせるには、その実行ファイルを `./austral` に置く。
戻すときは `cp -f _build/default/bin/austral.exe austral` とする。`make` は、ビルドが新しければ
`./austral` を書き戻さない。
* `case` の枝などを調べる関数を、途中で打ち切る形（`List.for_all` に述語を直接渡す形）に書き換えると、
後ろの枝を実行しなくなり、カバレッジの検査が落ちることがある。前のセッションで起きた。
* GitHub に書くコメントの末尾には、`Generated by Claude Code` の署名を付ける。
* 1 件ずつ、テスト、修正、記録、issue まで終えてから次へ進む。中途半端に残さない。
* セッションの終わりには、次を報告する。済みにした件数、残りの件数、「決定待ち」の一覧（推奨つき）、
新しく拒むようになった形、次のセッションが始める波。
