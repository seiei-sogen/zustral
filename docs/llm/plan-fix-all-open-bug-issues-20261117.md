### 2.3 棚卸しで見つけた、issue にない不具合

直さない。issue にするかどうかは、所有者が決める。

- 知らないエスケープ（`"\q"`）が、エラーにならず、C へそのまま書かれる。
- `Os.read_stream_to_string` が、ソースの先頭の空行を `String.trim` で落とす。先頭に空行が3つあると、6 行目のエラーが 3 行目として報告される。
- `run_command` が、子プロセスの stdout を読み切ってから stderr を読む。C コンパイラが stderr に多く書くと、止まるおそれがある（コードを読んだだけで、再現していない）。
- 内部エラーとコマンドラインのエラーは、`--error-format=json` を付けても、平文で出る。
- `read_string` が改行を数えないので、閉じていない文字列のエラーの桁がおかしい（`032/019` が「3 行目、98 桁」を固定している）。
- `Region` 宇宙の型引数に付けた制約が、名前が型クラスでありさえすれば通る。
- インスタンスの型引数の制約のエラーが、型引数の持ち主として型クラスの名前を言う。
- `generic [A: Free] instance TC(Int32)` のように、引数に現れない型引数を持つインスタンスが、宣言の時点で通る。呼ぶと、単相化の段で `Parameter list and argument list don't have the same length` になる（`033/004` が固定している）。
- 型クラスの型引数を使わないメソッド（`method answer(): Int32`）が、宣言の時点で通る。呼ぶと `No binding for this parameter: T` になる（`033/007` が固定している）。
- 自分を呼ぶたびに型引数が大きくなる汎用の関数（`Option[T]` を渡して自分を呼ぶ）で、コンパイルが終わらない。
- 組み込みのモジュールの中の位置が、ファイル名が空で、行が 1 つ多い（`cli/052` が固定している）。
- 無名の借用の領域が、エラーの文面に `_tmp_region_N` と出る。利用者が書いた名前がないからである。
- 取り込んだ定数の借用は、まだ「変数が見つからない」と出るはずである（コードを読んだだけで、実行していない）。
- 線形性の検査が、1つの関数の中の変数の数の3乗で遅くなる。`check_expr` が、式ごとにスコープの全変数を調べ、`get_entry` が毎回表を走査する。#143 のプログラムは `main` に N 個の変数を置くので、型が 400 個から 800 個で、まだ 4.2 倍になる。型ごとに関数を分けたプログラムでは 2.2 倍である。
- 本体の関数の定義の位置が、前のトークンの末尾から始まる。構文規則が、空になりうる `generic_segment` で始まるからである。

## 4. 単位に共通の規則

単位は、次の順で進める。`docs/plan.md` の2節と同じ規則である。

1. **失敗するテストを先にコミットする。** 直す前のコンパイラで実行し、失敗することを見る。テストは `/superpowers:test-driven-development` に従って書く。
2. **直す。** 原因の場所で直す。症状の出た場所に、検査を足して隠さない。
3. **検査を通す。** `nix-shell --command 'tools/refactoring/run-every-ci-check-locally.sh'` の14個が、すべて `ok` になる。計測値が変わったら、`tools/refactoring/measure.sh --record` で記録し直す。
4. **issue の再現の手順を、もう一度実行する。** 直す前の出力と、直した後の出力を、作業の記録に残す。

次のことを守る。

- テストは `test-programs/suites/` か `test-programs/cli/` に置く。OCaml の単体テストは、プログラムからは届かない行のためだけに使う。
- テストのディレクトリの名前は、何を確かめるかが分かる名前にする。
- `lib/BuiltInModules.ml` は、手で編集しない。`make` が作り直す。
- どのエラーの文面にもテストがあり、コンパイラのどの行もテストで実行される、という検査がある。新しいエラーには、それを出すプログラムを足す。
- コミットメッセージは日本語で書く。件名に issue の番号を入れる。
- 新しい関数は、原則として1ファイルに1関数にし、説明的な名前を付ける（`AGENTS.md`）。

## 5. 進め方

- S 列は、取りまとめ役が、主の作業ツリーで直列に行う。
- X、Y、Z の列は、列ごとに作業者を1つ置き、それぞれ自分の git の作業ツリーとブランチで進める。作業者は、2個から4個の単位を受け持って終わる。次のまとまりは、新しい作業者が受け持つ。
- 作業者は、終える前に、`claude/gifted-lamport-4f17ln` の先頭へ自分のブランチを載せ直し、検査を通し直す。
- `claude/gifted-lamport-4f17ln` へ取り込むのは、取りまとめ役だけである。取り込んだ先頭で、検査をもう一度実行する。通ったら push する。
- 作業の記録を書くのも、取りまとめ役だけである。
- X 列か Y 列が先に終わったら、その列の作業者が、Z 列の後ろの単位（Z10 から Z16）を引き取る。
