## 3. 単位

1つの単位は、原因を共有する項目のまとまりである。

### 3.1 順序と依存

単位は、4つの列に分けてある。列の中は、上から順に進める。列どうしは、並行して進める。

- **S 列**（足場）は、ほかの列より先に終える。作業ツリーでのビルドが、S1 に依存する。
- **X 列**は、コマンドラインの入口と、字句、構文、リテラルを扱う。
- **Y 列**は、名前の解決、宣言の検査、エラーの位置を扱う。
- **Z 列**は、型クラス、型の照合、単相化、C の生成を扱う。

列をまたぐ依存は、次のとおりである。

- X11（`Float32`）は、X9（単項の `-`）の後に行う。

## 4. 単位に共通の規則

単位は、次の順で進める。`docs/plan.md` の2節と同じ規則である。

1. **失敗するテストを先にコミットする。** 直す前のコンパイラで実行し、失敗することを見る。テストは `/superpowers:test-driven-development` に従って書く。
2. **直す。** 原因の場所で直す。症状の出た場所に、検査を足して隠さない。
3. **検査を通す。** `nix-shell --command 'tools/refactoring/run-every-ci-check-locally.sh'` の14個が、すべて `ok` になる。計測値が変わったら、`tools/refactoring/measure.sh --record` で記録し直す。
4. **issue の再現の手順を、もう一度実行する。** 直す前の出力と、直した後の出力を、作業の記録に残す。

次のことを守る。

- テストは `test-programs/suites/` か `test-programs/cli/` に置く。OCaml の単体テストは、プログラムからは届かない行のためだけに使う。
- テストのディレクトリの名前は、何を確かめるかが分かる名前にする。
- `lib/BuiltInModules.ml` は、手で編集しない。`make` が作り直す。
- どのエラーの文面にもテストがあり、コンパイラのどの行もテストで実行される、という検査がある。新しいエラーには、それを出すプログラムを足す。
- コミットメッセージは日本語で書く。件名に issue の番号を入れる。
- 新しい関数は、原則として1ファイルに1関数にし、説明的な名前を付ける（`AGENTS.md`）。

## 5. 進め方

- S 列は、取りまとめ役が、主の作業ツリーで直列に行う。
- X、Y、Z の列は、列ごとに作業者を1つ置き、それぞれ自分の git の作業ツリーとブランチで進める。作業者は、2個から4個の単位を受け持って終わる。次のまとまりは、新しい作業者が受け持つ。
- 作業者は、終える前に、`claude/gifted-lamport-4f17ln` の先頭へ自分のブランチを載せ直し、検査を通し直す。
- `claude/gifted-lamport-4f17ln` へ取り込むのは、取りまとめ役だけである。取り込んだ先頭で、検査をもう一度実行する。通ったら push する。
- 作業の記録を書くのも、取りまとめ役だけである。
- X 列か Y 列が先に終わったら、その列の作業者が、Z 列の後ろの単位（Z10 から Z16）を引き取る。
